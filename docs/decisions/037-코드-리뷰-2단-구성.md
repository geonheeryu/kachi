# 037. 코드 리뷰 2단 구성

## 배경

kachi의 검토 장치는 셋이다.
- 계획 단계에서 `tech-critic-lead`가 제안을 판정하고, 
- ArchUnit이 계층과 패키지 배치를 검사하고, 
- CI가 `./gradlew test`를 실행한다.
셋 모두 구현된 diff를 규칙에 비추어 읽지 않는다.
판정은 코드가 생기기 전에 끝나고, ArchUnit과 테스트는 기계로 표현한 규칙만 본다.

PR #15~#22는 작성 세션이 유일한 검토자였다.
PR #18은 ArchUnit 검사를 넓히면서 그동안 쌓인 규칙 위반 11건을 한꺼번에 고쳤다.
위반은 PR마다 들어왔지만 그 자리에서 읽은 사람이 없었고, 사람이 승인 전에 diff 전체를 읽는 방식으로는 이 양을 따라가지 못한다.

## 결정

리뷰를 2단으로 둔다.
1단은 PR 전에 로컬 리뷰어 둘이 문서에 적힌 kachi 규칙의 위반과 운영 중에 터질 범용 결함을 나눠 찾고, 2단은 PR 뒤에 CI 봇이 범용 결함을 다시 찾는다.
작성 세션은 기능 브랜치에서 커밋부터 봇과의 왕복까지를 승인 없이 하고(범위는 `AGENTS.md`의 작업 방식 절), 사람은 왕복이 끝난 PR을 읽고 병합한다.
리뷰어가 따르는 규칙은 두 지침 파일(`.agents/code-review-guideline.md`, `.agents/pr-review-common.md`)에 둔다.
봇의 통과 판정은 사람의 승인을 대신하지 않는다. 사람이 읽을 양을 줄이고, 사람이 판단해야 할 것을 질문으로 모아 올린다.

```
구현 ──> [1단] 지침 리뷰어 + 결함 리뷰어 ──> 커밋, push, draft PR ──> [2단] 검토 봇(CI) ──> ready ──> 사람이 읽고 병합
          (로컬 서브에이전트 둘, 병렬)        (승인 없음)               (별도 세션, 범용 결함)
               ^                                                           │
               └── 수정 또는 소명, 2회차까지                수정·소명 push, 2회차까지
```

### 1단은 로컬 서브에이전트 둘이 kachi 규칙과 범용 결함을 나눠 본다

- PR 전에 `pr-guideline-reviewer`와 `pr-defect-reviewer`를 함께 부른다. 범용 결함을 PR 뒤에만 보면 결함마다 push와 CI 실행이 한 번씩 더 든다.
  - 근거: "Most review now happens before a PR exists. … Then a subagent reviews the diff with fresh context." ([Anthropic, Solving code review at Anthropic](https://claude.dev/blog/solving-code-review-at-anthropic/))
- 리뷰어를 하나로 합치지 않는다. 지침 리뷰어는 근거 절을 인용할 수 있는 위반만 P0·P1로 지적하는데, 범용 결함에는 인용할 절이 없다. 한 리뷰어에 섞으면 인용 없는 지적이 kachi 규칙의 지적과 같은 모양으로 나오고, 작성 측이 반박할 근거도 없어 왕복만 는다.
  - 근거: "문서에 명시적으로 적힌 규칙만 보고, 인용할 수 없으면 침묵합니다." ([포스타입 팀 블로그](https://www.postype.com/@team/post/22652487))
- `pr-defect-reviewer`(`.claude/agents/pr-defect-reviewer.md`)는 2단 봇과 같은 지침 파일(`.agents/pr-review-common.md`, `.agents/pr-review-exclusions.md`)을 읽는다. 같은 모델이 같은 지침으로 두 번 보므로 2단이 새로 찾는 결함은 적다. 그래도 2단을 두는 것은 로컬 단계는 건너뛸 수 있고, 사람이 직접 한 커밋은 1단을 거치지 않으며, 지적과 소명의 기록이 PR에 남기 때문이다.
- 에이전트 정의(`.claude/agents/pr-guideline-reviewer.md`)에는 절차와 응답 형식만 두고, 등급과 판단 항목은 `.agents/code-review-guideline.md`에 둔다. 기준을 고칠 때 에이전트 정의를 건드리지 않기 위해서다.
- 기준 파일은 항목마다 핵심 규칙 한 줄과 원문 절을 함께 적는다. 절만 가리키면 리뷰어가 읽지 않은 절의 규칙을 놓치고, 본문을 옮겨 적으면 같은 내용이 두 문서에 생긴다. 한 줄은 찾기 위한 요약이고 판정은 원문으로 하며, 둘이 다르면 원문이 맞다고 기준 파일에 적었다. 원문 절을 고칠 때 이 한 줄도 함께 고쳐야 하는 비용을 받아들였다.
- 지침 리뷰어는 로컬에서 돌기 때문에 git에서 빠진 `WRITING.md`와 작업 중인 task 파일까지 읽는다.
- 리뷰어는 파일을 고치지 않는다. 고치는 일은 작성 세션이 한다. `git diff`에 Bash가 필요해 도구에서 빼지 못했고, 이를 지키는 것은 읽기 명령에만 쓰라는 에이전트 정의의 지시뿐이다.
- 두 리뷰어의 모델은 에이전트 정의에 `claude-fable-5-2`로 고정한다. 부른 세션의 모델을 물려받으면 판정 모델이 작성 세션의 모델 선택을 따라 내려간다.

### 2단은 CI 봇이 별도 세션에서 범용 결함만 본다

- `.github/workflows/pr-review.yml`이 PR마다 `anthropics/claude-code-action`을 모델 `claude-fable-5-2`로 실행한다.
- 검토 기준은 `.agents/pr-review-common.md`다. 바뀐 코드에서 결함이 생기는 입력이나 순서를 적을 수 있는 정확성, 동시성·정합성, 보안, 자원, 성능, 서비스 간 계약, 테스트 자체의 결함, CI·의존성의 결함만 본다. 테스트가 없다는 지적, 구조 제안, 이름과 서식은 보지 않는다. 범위를 좁힌 것은 사소한 지적이 쌓이면 사람이 봇 코멘트를 읽지 않게 되기 때문이다.
- 인라인 코멘트는 P0·P1에만 달고 P2는 요약에 개수만 남긴다. 결함에 가까운 P2를 놓칠 수 있는 비용을 받아들였다.
- 재검토는 이전 회차가 검토한 커밋 뒤에 바뀐 코드와 이전 지적만 본다. diff 전체를 매번 다시 보면 처음부터 있던 코드에서 새 지적이 계속 나와 왕복이 끝나지 않는다. 첫 회차에 놓친 결함은 다시 잡지 않는 비용을 받아들였다. 새로 바뀐 코드는 회차와 무관하게 검토한다.
- kachi가 정책으로 정한 것 가운데 범용 관점으로는 결함처럼 보이는 것은 `.agents/pr-review-exclusions.md`에 "지적하지 않는 것"으로 적어 공통 지침 뒤에 붙인다. 하위 호환과 데이터 이행의 누락, 어댑터에 재시도가 없다는 지적이 여기에 든다. 이 파일에는 봐야 할 것을 적지 않는다. 봐야 할 kachi 규칙은 지침 리뷰어의 몫이다.
- `claude_args`에 `--setting-sources user`를 둔다. 액션은 이 인자가 없으면 user, project, local 설정을 모두 불러오고, project 설정에는 `CLAUDE.md`를 거쳐 들어오는 `AGENTS.md`와 `.claude/settings.json`의 hook이 있다. project 설정을 빼면 kachi 규칙이 봇의 기준에 섞이지 않고, hook이 PR head의 `scripts/harness/hooks/pre_tool_use.py`를 CI에서 실행하는 일도 없다.
  - 근거: "Load settings from sources - prefer user's --setting-sources if provided, otherwise use all sources … (e.g., --setting-sources user to avoid in-repo configs)" ([base-action/src/parse-sdk-options.ts](https://github.com/anthropics/claude-code-action/blob/acfe7992852970efb4fee683d63d628e3e52df67/base-action/src/parse-sdk-options.ts))
- Read, Grep, Glob은 checkout 전체를 읽을 수 있으므로 봇이 `docs/`를 읽는 것까지 막지는 못한다. 공통 지침이 저장소 문서를 검토 기준으로 쓰지 말라고 지시한다.
- 판정 모델은 작성에 쓰는 모델보다 낮지 않게 둔다. 작성 모델이 놓친 결함을 같은 수준의 모델이 다시 놓치는 일을 줄이기 위해서다.
- 독립성은 작성 세션의 대화 맥락과 분리된 별도 세션이라는 데서 나오고, 작성 모델과 같은 회사의 모델이라는 한계가 있다. 요약의 "이전 지적" 줄에 해결됨, 소명됨, 남음의 건수가 남으므로, 지적 가운데 고쳐진 비율이 낮게 이어지거나 2단이 놓친 결함이 나오면 타사 모델의 리뷰 액션으로 바꾼다. 모델은 워크플로의 한 줄이다.
- 인증은 저장소 secret `CLAUDE_CODE_OAUTH_TOKEN`이다. secret 등록은 사람 몫이다(`docs/user-intervention.md` 6번).

### 봇은 결과만 내고 코멘트는 스크립트가 쓴다

- 워크플로를 job 둘로 나눈다. `review` job은 PR 내용을 모델에 넣고 JSON 결과(`--json-schema`, 액션 출력 `structured_output`)만 낸다. `post` job은 `scripts/harness/pr_review.py`가 그 결과를 검증해 인라인 코멘트와 요약을 쓴다.
- 신뢰할 수 없는 입력을 읽는 쪽과 쓰기 권한을 가진 쪽을 떼어 놓기 위해서다. 저장소가 PUBLIC이고, 주입된 지시가 봇에게 토큰이나 secret을 코멘트로 내보내게 한 공개 사례가 이 액션에 있다. `review` job에는 쓰기 권한과 셸이 없고, `post` job은 PR 내용을 모델에 넣지 않는다.
- 회차, 지적 번호, 판정, 게시 상한, P0의 소명 거부는 봇이 아니라 스크립트가 정한다. 모델이 세고 계산하면 실행마다 달라질 수 있는 값이기 때문이다. 그 규칙은 `.agents/pr-review-common.md`의 "스크립트가 정하는 것" 절에 있다.
- 요약 코멘트 끝의 숨은 주석에 지적 목록과 검토한 커밋을 JSON으로 남기고, 다음 회차는 그것을 읽는다. 다른 계정이 요약을 흉내 내지 못하게 `github-actions[bot]`이 쓴 코멘트만 이전 요약으로 본다.
- 스크립트는 토큰 꼴의 문자열(`sk-ant-`, `ghs_` 등)을 코멘트에서 가린다. 주입된 지시가 판정 자체를 바꾸는 것까지는 막지 못한다.

### 지적은 등급을 달고, 판단할 수 없는 것은 질문으로 올린다

- 등급은 P0 차단, P1 수정 필요, P2 권장, 질문 넷이다. 정의와 해제 조건의 원본은 지침 리뷰가 `.agents/code-review-guideline.md`, 결함 리뷰와 2단이 `.agents/pr-review-common.md`다.
- P0은 소명으로 내려가지 않는다. PR 작성자와 승인하는 사람이 같은 계정이라 봇은 사람의 해제와 작성 세션의 소명을 구분할 수 없고, 소명으로 내려가게 하면 작성 측이 아무것도 고치지 않고 차단을 풀 수 있다. 사람이 P0을 받아들이는 방법은 봇의 판정과 무관하게 병합하는 것이다.
- 발송 경로의 특수 분기는 정합성 결함이 아니어도 지침 리뷰의 P0으로 둔다. 관리자 분기를 근거를 달아 통과시키는 길을 열지 않기 위해서다. 어댑터의 in-process 재시도 루프는 관례 위반이라 P1이다.
- 소명된 P1은 요약의 소명 목록에 남는다. 사람은 승인할 때 이 목록만 따로 읽으면 된다.
- 모든 리뷰 요약은 본 범위와 못 본 범위를 적는다. 읽지 않은 파일과 실행하지 않은 검증이 못 본 범위다.
- ArchUnit이 이미 검사하는 규칙은 리뷰 지침에서 뺀다. 기계로 검사할 수 있는데 검사가 없는 규칙은 지적하면서 "ArchUnit 후보"로도 보고하고, 검사로 옮길지는 사람이 정한다.

### 왕복은 2회차에서 끊는다

- 작성 측은 지적마다 고치거나 소명한다. 왕복 스킬 `pr-review`(`.agents/skills/pr-review/SKILL.md`)가 1단 실행, 커밋과 draft PR 생성, 2단 코멘트 수집, 수정과 소명을 맡는다.
- 2회차에 남은 P0·P1은 더 고치지 않고 사람에게 올린다. 봇과 작성 측이 합의하지 못한 지적은 회차를 늘려도 좁혀지지 않고, 사람이 정하는 편이 빠르다. 2라는 숫자를 뒷받침하는 측정은 없다.
- 2단의 회차는 push마다 오르므로 리뷰와 무관한 push도 회차를 올린다. 그래서 2단은 회차로 새 지적을 막지 않고, 3회차부터 이전 지적 가운데 남은 것을 사람이 확인하라고 요약에 적기만 한다. 같은 코드를 두고 왕복이 이어지는 것은 재검토 범위를 바뀐 코드로 좁힌 것이 막는다.
- 1단은 스킬이 부르는 횟수가 곧 회차라, 지침 리뷰어는 3회차 이상으로 불리면 새 지적을 P0만 낸다.
- 소명은 PR의 일반 코멘트에 지적 번호를 적어 단다. 스크립트가 봇에게 넘기는 것이 PR 작성자의 일반 코멘트뿐이기 때문이다. 트리거가 `pull_request`뿐이라 코드 수정 없이 소명만 달면 스킬이 워크플로를 다시 실행한다. 재실행은 원래 이벤트의 커밋으로 돌기 때문에, 스크립트는 그 커밋이 PR의 현재 head가 아니면 검토하지 않는다.

### 기능 브랜치의 커밋, push, draft PR은 승인 없이 하고 병합은 사람만 한다

- 작성 세션은 1단이 통과하면 커밋하고 push해 draft PR을 만들고, 2단과의 왕복이 끝나면 PR을 ready로 바꾼다. 사람이 PR을 만들기 전에 승인하면 봇이 아직 보지 않은 diff를 읽게 되고, 왕복마다 승인하면 회차마다 사람을 기다린다. 왕복이 끝난 뒤에는 판정 줄, 남은 지적, 소명 목록, 못 본 범위가 붙은 PR을 한 번 읽으면 된다.
- draft는 사람이 볼 차례가 아니라는 표시다. 2단은 draft PR에서도 돈다.
- 병합은 사람만 한다. 작성도 검토도 같은 모델이 하므로 사람의 병합이 유일한 독립 검토다. 변경의 위험도로 골라 자동 병합하는 방식은 revert 이력 같은 위험 데이터가 없어 들이지 않았다.
- 승인을 없앤 자리는 기계가 막는다.
  - 훅(`scripts/harness/hooks/pre_tool_use.py`)이 PR 병합, 강제 push, `main`으로의 push, 검사를 건너뛰는 옵션(`--no-verify`, `core.hooksPath`)을 차단한다. 작성 세션은 사용자의 토큰으로 동작해 GitHub이 둘을 구분하지 못하므로, 병합을 사람만 하게 만드는 장치는 이 훅이다.
  - `main` 브랜치의 보호 규칙과 secret push protection은 저장소 설정이라 사람 몫이다(`docs/user-intervention.md` 6번). 저장소가 PUBLIC이라 push된 비밀 값은 되돌릴 수 없다.
  - pre-push 훅이 push마다 문서 검사와 `verify.fast`를 실행한다.
  - 훅(`scripts/harness/hooks/`, `scripts/harness/githooks/`), 훅을 거는 `.claude/settings.json`과 `.claude/settings.local.json`, 2단 워크플로는 `harness.json`의 `frozen_paths`에 넣어 훅이 편집을 막는다. 훅은 작업 트리의 파일을 실행하므로 push 승인만으로는 편집하는 순간 차단이 꺼지는 것을 막지 못한다. 이 파일들을 고치려면 사람이 `frozen_paths`에서 경로를 뺀다.
  - 리뷰 기준과 차단 장치를 바꾼 커밋은 승인 뒤에 push한다. 작성 세션이 자기를 검토하고 막는 장치를 스스로 고치는 경로이기 때문이다. 대상 경로는 `PROTECTED_PATHS`와 같고, 승인 없이 push돼도 2단 요약의 질문에 드러난다.
- 남은 P0이 있거나 CI 테스트가 실패한 PR은 ready로 바꾸지 않고 draft인 채 사람에게 올린다.
- 왕복 상한이 유일한 제동이므로 2회차 규칙은 승인을 없앤 뒤에도 그대로 둔다. 봇의 회차는 실행이 건너뛰어지거나 결과가 비면 오르지 않으므로, 스킬은 세션이 한 수정 push와 재실행도 2번까지로 따로 세고, 요약의 검토 커밋과 회차가 기대와 다르면 멈춘다.
  - 근거: "One CLI PR went through more than fifty rounds of review and fixes overnight before its author stopped it." 같은 글이 3회 상한을 대응으로 든다. ([Anthropic, Solving code review at Anthropic](https://claude.dev/blog/solving-code-review-at-anthropic/))

### 2단 워크플로의 보안 기준

저장소가 PUBLIC이고 워크플로가 secret을 외부 액션에 넘기므로 아래를 모두 지킨다.

- 트리거는 `pull_request`만 쓴다. `pull_request_target`은 base 저장소의 secret을 가진 채 돌기 때문에 쓰지 않는다.
- job 조건 `github.event.pull_request.head.repo.full_name == github.repository`와 액션 입력 `allow_fork_prs: "false"`를 함께 둔다. 액션의 `allow_fork_prs` 기본값은 `"true"`다(`action.yml`). 이 두 조건 때문에 봇이 검토하는 PR은 저장소에 쓰기 권한이 있는 사람이 같은 저장소 브랜치로 연 것뿐이다.
- `review` job의 `permissions`는 `contents: read`, `pull-requests: read`, `issues: read`다. 쓰기 권한은 `post` job의 `pull-requests: write` 하나다.
- 액션에 `github_token: ${{ github.token }}`을 넘긴다. 이 입력이 없으면 액션은 OIDC 토큰을 Claude GitHub App 설치 토큰으로 바꿔 쓰고, 그 토큰의 권한은 워크플로의 `permissions`가 아니라 App 설치 권한이 정한다. 입력을 넘기면 교환을 건너뛰므로 `id-token: write`와 App 설치가 필요 없고, 봇의 세션에 있는 GitHub 토큰은 읽기 전용 워크플로 토큰뿐이다. `CLAUDE_CODE_OAUTH_TOKEN`은 액션의 환경에 남는다. 봇에게 셸이 없고 스크립트가 토큰 꼴의 문자열을 가리지만, Read 도구로 프로세스 환경을 읽을 수 있는지는 확인하지 못했다.
  - 근거: `setupGitHubToken()`은 `OVERRIDE_GITHUB_TOKEN`이 있으면 그것을 돌려주고 OIDC 교환을 하지 않는다([src/github/token.ts](https://github.com/anthropics/claude-code-action/blob/acfe7992852970efb4fee683d63d628e3e52df67/src/github/token.ts)). `action.yml`에서 `OVERRIDE_GITHUB_TOKEN`은 `inputs.github_token`이다.
- `claude_args`에 `--permission-mode default`를 둔다. 액션의 기본은 auto 모드이고, auto 모드에서 `--allowedTools`는 엄격한 경계가 아니다.
  - 근거: "By default the action uses auto mode, where a safety review decides tool calls that your allow rules don't cover. … For a strict list of what Claude may run, use `--permission-mode acceptEdits` or `default`." ([docs/security.md](https://github.com/anthropics/claude-code-action/blob/acfe7992852970efb4fee683d63d628e3e52df67/docs/security.md))
- `--allowedTools`는 Read, Grep, Glob과 구조화 결과를 내는 도구뿐이다. Bash, 편집 도구, 웹 도구는 `--disallowedTools`로 막는다. 봇은 PR의 코드를 실행하지 않고 `gh`도 부르지 않는다. 봇이 읽을 PR 정보와 diff는 앞 단계의 스크립트가 워크플로 토큰으로 받아 `.pr-review-input/`에 쓴다.
- `--max-turns 40`을 둔다. 상한에 걸리면 결과가 없어 `post` job이 돌지 않고, 사람은 요약이 없는 PR을 봇 미완료로 본다. 충돌이 있는 PR도 `pull_request` 워크플로가 돌지 않아 요약이 없다.
- 공통 지침, "지적하지 않는 것" 파일, 스크립트는 워크플로가 PR의 base 커밋에서 꺼내 `$RUNNER_TEMP`에 쓰고, 지침은 그 경로를 `--append-system-prompt-file`로 넘긴다. `post` job은 base 커밋을 checkout해 스크립트를 실행한다. 액션은 쓰기 권한이 있는 작성자의 PR에서는 입력이 가리키는 파일을 base 것으로 바꾸지 않기 때문이다.
  - 근거: "On pull requests from authors without write access, the action also replaces … On these pull requests, files and directories in the checkout that your workflow's inputs name also come from the base branch where the pull request changes them … `--append-system-prompt-file` …" ([docs/security.md](https://github.com/anthropics/claude-code-action/blob/acfe7992852970efb4fee683d63d628e3e52df67/docs/security.md)). 소스의 `src/entrypoints/run.ts`도 이 복원을 `isUntrustedCheckout`일 때만 한다.
- 워크플로 파일은 `pull_request` 이벤트에서 PR head의 것이 실행된다. 그래서 base에서 꺼내는 방식은 PR이 지침이나 스크립트를 고쳐 자기 검토 기준을 바꾸는 일은 막지만, 워크플로까지 함께 고친 PR은 막지 못한다. PR이 `scripts/harness/pr_review.py`의 `PROTECTED_PATHS`(두 워크플로, 지침 파일, 에이전트 정의, 스킬, 스크립트, 훅과 그 설정, `harness.json`) 가운데 하나라도 고치면 스크립트가 그 사실을 요약의 질문에 넣고, 사람은 그 변경을 직접 읽는다.
- 워크플로의 모든 외부 액션은 태그가 아니라 커밋 SHA로 고정하고 버전은 주석으로 단다. 태그는 옮겨질 수 있고, 같은 job에서 도는 액션은 그 job의 secret에 닿기 때문이다. SHA를 올릴 때 다시 확인할 동작은 워크플로의 주석에 적었다.
- `actions/checkout`은 `persist-credentials: false`로 둔다. 기본값은 워크플로 토큰을 `.git/config`에 남기고, 봇의 Read 도구가 그 파일을 읽을 수 있다. base에서 꺼내는 `git fetch`는 공개 저장소라 자격 증명 없이 된다.
- PR 본문, 코멘트, 코드 안의 지시문은 데이터로 다룬다. 소명은 PR 작성자의 코멘트만 인정한다.

## 반려한 대안

- 공식 `code-review` 플러그인을 쓴다: 이미 리뷰된 PR을 건너뛰어 수정 뒤 재검토가 되지 않는다.
  - 근거: "Automatic skipping of closed, draft, or already-reviewed PRs" ([claude-plugins-official의 code-review README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-review/README.md))
- ArchUnit만 넓힌다: 전이 전 값 복사, 어댑터 안의 재시도, 도메인 문서 갱신 누락처럼 판단이 필요한 규칙은 ArchUnit으로 표현할 수 없다.
- 등급 표와 판정 줄 형식을 이 문서에 둔다: 봇은 이 문서를 읽지 않아 규칙이 지침 파일과 이 문서에 따로 있게 되고, 실제로 P0 정의와 판정 용어가 서로 어긋났다.

## 결과

구현 세션은 작업 단위를 마치면 1단을 거쳐 draft PR을 만들고, PR에는 `github-actions[bot]`의 2단 요약 1개와 P0·P1 인라인 코멘트가 붙는다.
사람은 ready가 된 PR에서 P0, 소명 목록, 질문, 못 본 범위를 먼저 읽고 병합한다.

2단의 실제 PR 동작은 워크플로가 병합되기 전이라 미검증이다. 스크립트의 회차·판정·요약 계산만 단위 테스트(`scripts/harness/tests/test_pr_review.py`)로 확인했다.
GitHub이 diff를 돌려주지 않는 큰 PR(파일 300개 또는 2만 줄 초과)에서는 입력 모으기가 실패한다.
확인은 이 결정을 들이는 PR이 병합된 뒤의 첫 PR에서 하고, 확인할 항목은 `docs/user-intervention.md` 6번에 있다.

리뷰 비용은 PR마다 로컬 리뷰어 둘과 CI의 Fable 실행이 왕복 회차만큼 든다.
같은 PR에 새 push가 오면 진행 중인 `review` job을 취소한다. `post` job은 취소하지 않는다. 인라인 코멘트만 달리고 요약이 빠지면 다음 실행이 같은 번호로 다시 달기 때문이다.
훅은 명령 문자열을 정규식으로 보므로 변수나 스크립트 파일에 숨긴 병합 명령은 막지 못하고, Bash의 리다이렉트로 동결 경로에 쓰는 것도 보지 않는다. `harness.json`은 동결하지 않아 작성 세션이 `frozen_paths`를 고칠 수 있고, 그 변경은 diff에 드러난다. `main` 보호 규칙이 걸리기 전에는 이 훅과 지시 파일만이 `main`을 지킨다.
