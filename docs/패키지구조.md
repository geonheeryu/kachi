# 패키지 구조

- 모든 모듈이 따르는 패키지 배치 규칙이다.  
층의 책임과 의존 방향은 [아키텍처.md](아키텍처.md), 코드 모양 관례는 [개발가이드.md](개발가이드.md)에 있다.

```text
me.rgunny.kachi.{service}
├── domain
├── application
│   ├── port
│   │   ├── inbound
│   │   └── outbound
│   ├── service
│   └── exception
├── adapter
│   ├── inbound
│   └── outbound
└── config
```

## application/port

- `inbound`/`outbound`로 쓴다. `in`은 Kotlin 키워드라 패키지 이름으로 쓰면 import마다 백틱이 붙는다.
- `<feature>/` 루트에는 어댑터가 구현하는 인터페이스만 두고, 파라미터·리턴 타입은 `<feature>/model/`에 둔다.
  - 예: `port/outbound/sender/NotificationSender.kt`, `port/outbound/sender/model/SendNotificationCommand.kt`
  - 이름이 `dto`가 아니라 `model`인 것은 이 타입이 전송 경계를 넘는 직렬화 객체가 아니라 프로세스 안 유스케이스 경계의 계약이기 때문이다. `dto`는 vendor·다른 서비스의 요청·응답과 HTTP 요청·응답에 쓴다.
  - 포트가 도메인 객체만 주고받으면 그 feature에 `model/`을 만들지 않는다.
- `model/`을 종류로 다시 가르지 않는다.
- `model/`이 10개를 넘으면 feature를 나눈다.
  - 예: `port/inbound/{admin,dispatch,dlt,outbox,request}/`
- 여러 포트가 쓰는 타입은 생산자 포트의 feature에 둔다.
- `model/`에는 포트 시그니처에만 쓰이는 타입을 둔다.
  - 예: `port/inbound/request/model/RequestNotificationCommand.kt`
- 도메인 로직이 직접 다루는 타입은 `domain/`에 둔다.
  - 예: `domain/Notification.kt`
- `model/` 타입을 도메인 로직이 다루게 되면 `domain/`으로 올린다.
- `domain/` 타입이 한 포트의 시그니처에만 쓰이면 그 포트의 `model/`로 내릴지 검토한다.
- outbox 영속·publisher·serializer 포트는 `outbox/` 하나에 둔다.
  - 예: `port/outbound/outbox/{NotificationOutboxPersistencePort, NotificationDispatchPublisher, NotificationEventSerializer}.kt`

## application/service·exception

- `service/`는 `port/inbound/<feature>/`와 같은 이름으로 나눈다. 유스케이스가 셋 이하면 평면이다.
  - 예: `service/{admin,dispatch,dlt,outbox,request}/`
- 서비스 안에서만 쓰는 정책·결과 타입은 그 서비스 옆에 둔다.
  - 예: `service/dispatch/DispatchNotificationPolicy.kt`
- `exception/`은 평면이다. 모듈 예외·에러 코드 인터페이스·기능별 에러 코드 enum과 예외를 나란히 둔다.
  - 예: ai `application/exception/{AiException, AiErrorCode, AiOutboxErrorCode, AiOutboxPublishException}.kt`

## domain

- 하위 패키지는 aggregate 하나와 그 VO·enum·정책, 또는 한 외부 연동의 실패 모델이다. 나머지는 평면이다.
  - 예: `domain/retry/`

## adapter

- inbound·outbound가 함께 쓰는 횡단 관심사 클래스는 `adapter/<역할>/`에 둔다.
  - 예: `adapter/monitoring/`

## adapter/inbound

- 1단은 진입 기술이다.
  - 예: `adapter/inbound/{messaging,scheduler,web}/`
- 스케줄러와 컨트롤러가 함께 부르는 실행기는 기능 이름 패키지에 둔다.
  - 예: collector `adapter/inbound/{collection,outbox}/`
- 요청·응답 DTO는 컨트롤러 옆에 둔다.
- 컨트롤러가 셋 이상이면 feature 하위 `web/<feature>/{request,response}/`로 가른다.
  - 예: `web/admin/{request,response}/`
- `web/response/`는 공통 응답 형식 전용이며 엔드포인트별 DTO는 두지 않는다.
  - 예: `web/response/{ErrorCode, FieldError}.kt`
- 경계 전용 예외는 그 경계 아래 `exception/`이다.
  - 예: `messaging/exception/InvalidDispatchMessageException.kt`

## adapter/outbound

- 1단은 그 어댑터가 구현하는 포트 패키지의 이름이다.
  - 예: 포트 `port/outbound/sender/`의 어댑터는 `adapter/outbound/sender/`
- vendor 구현이 여럿이면 포트 아래 vendor 패키지다.
  - 예: `sender/{slack,discord,telegram}/`
- 같은 기술을 쓴다는 이유만으로 묶지 않는다.
  - 예: worker의 Redis 어댑터는 `idempotency/`와 `recipient/`에 따로 있다
- 포트가 다른 어댑터들이 같은 구현 클래스(client, repository, document, mapper)를 함께 써야 할 때만 1단을 기술 이름으로 하고 그 아래를 포트 이름으로 나눈다.
  - 예: story의 `tei/{embedding,judge}/`
- Spring Data repository·document는 항상 `persistence/<포트 이름>/`이다.
  - 예: `persistence/{dlt,notification,outbox}/`
- 어댑터끼리만 쓰는 계약·데코레이터·분류기·codec과 그 어댑터가 부르는 외부 시스템의 health indicator는 1단 패키지 루트다.
  - 예: `sender/{MeteredNotificationSender, VendorHttpExceptionClassifier}.kt`, story `tei/TeiHealthIndicator.kt`
- vendor·다른 서비스의 요청·응답 형태 그대로인 타입은 `dto/`다.
  - 예: `sender/telegram/dto/`, `recipient/dto/`
- 하위 패키지는 포트 이름·vendor 이름·`dto/` 세 종류뿐이다.

## config

- 평면이다.
- 파일명은 `<기능>Config`·`<기능>Properties`, vendor 조립은 `<Vendor>…Config`다.
  - 예: `config/{NotificationRecipientConfig, NotificationRecipientProperties, TelegramNotificationSenderConfig}.kt`
- `@ConfigurationProperties`는 `config/`에만 둔다.
- adapter·application은 `*Properties`를 받지 않는다. config의 `@Bean`이 primitive, 어댑터 옆의 `*Settings`, 서비스 옆의 `*Policy`로 값을 넘긴다.
  - 예: routing `NotificationRoutingConfig` -> `UserServiceRecipientReaderSettings`·`RoutingPolicy`

## 테스트

- `src/test`는 main 패키지를 미러한다.
  - 예: `sender/telegram/TelegramNotificationSenderTest.kt`
- test 루트에는 `fake/`(포트 Fake), `fixture/`(고정 시간·테스트 데이터), `support/`(stub 서버 등 시험 도구), `architecture/`(ArchUnit)를 둔다.
- 실제 외부 서버를 부르는 테스트는 `src/realTest`다.
  - 예: story `src/realTest/.../adapter/outbound/tei/`

## ArchUnit 슬라이스

- 1단 패키지는 순환이 없고, `adapter/outbound` 바로 아래 패키지는 서로 의존하지 않는다.
- `adapter/outbound` 1단 이름은 모듈별 허용 목록으로 검사한다. 허용 목록은 그 모듈의 포트 패키지 이름과, 포트가 다른 어댑터들이 구현 클래스를 함께 쓰는 기술 이름(`persistence`, story의 `tei`)이다. 2단 이하의 이름과 구현 클래스를 실제로 함께 쓰는지는 검사하지 않는다.
- 클래스를 함께 쓰는 어댑터는 같은 슬라이스에 둔다.
  - 예: `sender/VendorHttpExceptionClassifier`를 `sender/{slack,discord,telegram}`이 공유한다
- 포트 패키지 루트(`application/port/{inbound,outbound}/<feature>/`)의 타입이 인터페이스인지 위치로 검사한다. 이름의 접미어는 보지 않는다. 루트의 인터페이스가 어댑터가 구현하는 포트인지 파라미터 타입인지는 검사하지 않는다.
- inbound 어댑터는 outbound 포트를 구현하지 않는다.
