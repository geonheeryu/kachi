# 전체 사이클 스모크

실제 뉴스 provider, TEI, LLM(같은 머신의 Ollama), 채널(Slack·Discord·Telegram)로 수집 -> story 조립 -> 요약 -> 알림 수신을 사람이 확인하는 절차다.
테스트는 실제 provider와 vendor를 부르지 않으므로([테스트전략.md](테스트전략.md)), 실제 연결은 여기서만 확인한다.
자동 검증은 `./gradlew :e2e-test:e2eTest`가 뉴스·TEI·LLM stub과 mock sender로 같은 경로를 돈다.

관련 결정: ADR 029(전체 사이클 검증과 e2e-test 모듈), ADR 035(notification-routing의 story 요약 소비와 storyId 멱등).

## 전제

- Docker Desktop이 기동되어 있다.
- TEI 컨테이너를 한 번 띄워 모델 가중치를 받아 두었다([user-intervention.md](user-intervention.md) 3번).
  ```sh
  ./scripts/infra.sh tei start
  ```
  - `cycle.sh`는 volume `kachi_tei-data`가 없으면 TEI를 띄우지 않고 실패한다.
- Ollama 서버가 로컬에 기동되어 있다. local 프로파일의 LLM 후보가 Ollama 하나라 LLM API 키는 필요 없다.
  ```sh
  ollama serve
  ollama pull qwen3.8:27b     # 18GB. ai-service LlmModel.OLLAMA_QWEN3_27B의 wire id
  ```
  - 다른 주소에 있으면 `KACHI_AI_LLM_PROVIDERS_OLLAMA_BASEURL`로 준다.
  - 후보 모델은 코드에 있어 env로 바꾸지 않는다.
- 실호출 검증이 통과한다. Ollama의 모델 목록과 생성 1회를 확인한다(`ai-service/README.md`의 realTest 절).
  ```sh
  ./gradlew :ai-service:realTest
  ```
- 저장 형식이 바뀐 코드로 처음 띄우는 것이면 `./scripts/cycle.sh reset`으로 데이터를 먼저 지운다. 사이클의 데이터는 기동 시 다시 만들어진다([재실행](#재실행)).
- `.env.local`에 다음 키가 있다. 키 목록은 `.env.example`.

| 키 | 용도 |
| --- | --- |
| `KACHI_USER_SEED_ADMIN_SLACK_WEBHOOK_URL` | 관리자 계정의 Slack 바인딩 주소. `https://hooks.slack.com/`으로 시작해야 한다 |
| `KACHI_USER_SEED_ADMIN_DISCORD_WEBHOOK_URL` | 관리자 계정의 Discord 바인딩 주소. `https://discord.com/api/webhooks/`로 시작해야 한다 |
| `KACHI_USER_SEED_ADMIN_TELEGRAM_CHAT_ID` | 관리자 계정의 Telegram chat id |
| `KACHI_NOTIFICATION_TELEGRAM_BOT_TOKEN` | worker의 Telegram 봇 토큰 |
| `NAVER_CLIENT_ID`·`NAVER_CLIENT_SECRET`, `FINNHUB_API_KEY` | collector-service 뉴스 provider의 credential. 키가 없는 provider는 `KACHI_COLLECTOR_PROVIDERS_NAVER_ENABLED=false`·`KACHI_COLLECTOR_PROVIDERS_FINNHUB_ENABLED=false`로 끄고, 켠 provider에 키가 없으면 collector가 기동에 실패한다 |

Google News RSS provider는 키가 없고 local 프로파일에서 켜져 있다.

수신자는 local seed의 관리자 계정(`admin@kachi.local`)이다.

- seed가 이 계정에 세 채널 바인딩을 위 주소로 만든다.
- 시드 키워드 5개(`TRUMP`·`NVIDIA`·`SPACE-X`·`TESLA`·`이란`)를 세 채널로 구독시킨다.
- 공개 API로 구독을 넣으려면 OAuth 로그인이 필요해서 seed가 대신한다.

## 기동

```sh
./scripts/cycle.sh start
```

순서: TEI(tei-embedding·tei-reranker) -> 인프라(mysql·redis·mongo·kafka, qdrant) -> Kafka 준비 대기 -> Mongo index 스크립트 2개 -> user-service -> Ollama 확인 -> 나머지 6개.

- 나머지 6개는 collector-service, story-service, ai-service, notification-routing, notification-service, notification-worker다.
- story-service는 TEI 두 서버와 Qdrant가 떠 있어야 기동한다. `cycle.sh`는 TEI 컨테이너가 healthcheck를 통과할 때까지 기다린다.
- ai-service의 이벤트 발행·relay·scheduler와 Ollama 후보는 local 프로파일이 켠다. 스크립트가 env로 덮는 값은 없다.
- local 프로파일에서 켜지는 주기 작업은 다음과 같다. 아래 절차는 기다리지 않고 internal API로 일으킨다.
  - collector 뉴스 수집: 기동 30초 뒤부터 10분마다 활성 키워드 전체를 수집한다.
  - ai story 요약 tick: 기동 1분 뒤부터 5분마다 `max-wait`(60m)을 넘긴 story를 요약한다.
  - ai 키워드 확장: 기동 5분 뒤부터 24시간마다 Ollama를 부른다.

기동 확인:

```sh
./scripts/cycle.sh status
for port in 8080 8082 8083 8084 8085 8086 8087; do curl -s "localhost:$port/actuator/health"; echo; done
```

포트는 user-service 8080, collector-service 8082, ai-service 8083, notification-service 8084, notification-worker 8085, notification-routing 8086, story-service 8087이다.

## 확인 절차

각 단계의 결과를 보고 다음으로 간다. 막히면 해당 서비스 로그(`./scripts/app.sh <service> logs`)를 본다.
아래 명령은 셸 변수 `ADMIN_ID`와 `STORY_ID`를 이어 쓰므로 같은 셸에서 실행한다.

1. **seed 확인**
   - 관리자 바인딩이 실주소로 들어갔는지, 시드 키워드의 수신자로 관리자가 나오는지 본다.
   ```sh
   ADMIN_ID=$(curl -s 'localhost:8080/api/v1/internal/users?role=ADMIN' | jq -r '.data[0].userId')
   curl -s "localhost:8080/api/v1/internal/users/$ADMIN_ID/channel-bindings/SLACK" | jq .data
   curl -s -X POST localhost:8080/api/v1/internal/subscriptions/recipients/search \
     -H 'Content-Type: application/json' -d '{"keywords":["NVIDIA"],"cursor":null}' | jq .data
   ```
   - 바인딩의 `status`가 `ACTIVE`이고 `address`가 `.env.local`의 값이어야 한다. `DISCORD`, `TELEGRAM`은 경로의 채널만 바꿔 본다.
   - `keywords`에 `{"canonicalKey":"nvidia","displayName":"NVIDIA"}`가 있어야 한다.
   - `recipients`에 관리자 `userId`가 `SLACK`·`DISCORD`·`TELEGRAM` 세 항목으로 있어야 한다.
   - seed 사용자 `collector-admin@kachi.local`도 `SLACK` 한 항목으로 나온다. 바인딩 주소가 자리표시 값이라 이 항목의 발송 결과는 아래에서 보지 않는다.
2. **뉴스 수집**
   - collector가 키워드 하나로 수집한다. body를 빼면 user-service의 활성 키워드 전체를 수집한다.
   ```sh
   curl -s -X POST localhost:8082/api/v1/internal/collections/news \
     -H 'Content-Type: application/json' -d '{"keywords":["nvidia"]}' | jq .data
   ```
   - `collectedCount`가 새로 저장한 기사 수다. 0이면 provider 키나 네트워크를 본다.
   - 409는 scheduler의 수집이 도는 중이라는 뜻이다. 끝난 뒤 다시 부른다.
   - 새 기사마다 outbox relay가 `collector.news.collected`를 낸다. relay는 기동 15초 뒤부터 5초마다 돈다.
3. **story 조립 확인**
   - story-service가 기사를 임베딩하고 기존 story에 붙이거나 새 story를 연다.
   ```sh
   ./scripts/app.sh story-service logs      # "collector news consumed newsId=... storyId=... decision=... replayed=false" 확인
   curl -s 'localhost:8087/api/v1/internal/stories?status=OPEN&limit=50' \
     | jq '.data[] | select(.keywords | index("nvidia")) | {id, articleCount, keywords, openedAt}'
   ```
   - 목록은 연 시각의 역순이다. `articleCount`가 3 이상인 story의 `id`를 고른다.
   ```sh
   STORY_ID=<고른 story의 id>
   curl -s "localhost:8087/api/v1/internal/stories/$STORY_ID" | jq '.data.articles[] | {title, source, attachedAt}'
   ```
   - 기사가 붙을 때마다 story-service가 `story.article.attached`를 낸다.
   - `collector news assembly failed and will be retried` 로그가 반복되면 TEI 컨테이너(`./scripts/infra.sh tei logs`)를 본다.
4. **story 요약과 outbox 확인**
   - 미요약 기사가 `min-new-articles`(3)건에 닿으면 ai-service가 `story.article.attached`를 받은 자리에서 Ollama로 요약한다.
   - 27B 모델은 요약 한 건에 분 단위가 걸린다.
   ```sh
   ./scripts/app.sh ai-service logs      # "story article consumed newsId=... storyId=... replayed=false summary=CREATED(v1, DEVELOPMENT)" 확인
   curl -s "localhost:8083/api/v1/internal/ai/story-summaries?storyId=$STORY_ID" \
     | jq '.data[] | {version, developmentKind, keywords, sourceNewsCount, title}'
   curl -s 'localhost:8083/api/v1/internal/ai/outboxes?status=PUBLISHED' | jq '.data[] | {eventType, eventKey, status}'
   ```
   - 요약 버전 1이 `DEVELOPMENT`로 있어야 한다. `DEVELOPMENT` 버전만 `ai.summary.created`를 내고 `NO_CHANGE` 버전은 이벤트가 없다.
   - outbox에 `SUMMARY_CREATED` 행이 몇 초 안에 `PUBLISHED`가 되어야 한다. `status`를 빼면 `DEAD` 행만 조회된다.
   - 미요약 기사가 3건에 못 미치는 story는 tick이 `max-wait`(60m)을 넘긴 뒤 요약한다. 그 tick을 지금 한 번 돌리려면 다음을 부른다.
   ```sh
   curl -s -X POST localhost:8083/api/v1/internal/ai/story-summaries/run | jq .data
   ```
   - 요약이 실패하면 `GET /api/v1/internal/llm/models`로 ollama 모델의 상태(서킷·cooldown·hold)를 본다.
   - 같은 story가 연속 3회 실패하면 격리된다. `GET /api/v1/internal/ai/story-quarantines`로 보고, 격리 알림은 관리자 채널로 간다.
5. **라우팅**
   - routing이 story의 키워드로 수신자를 페이지 단위로 읽고 수신자 x 채널마다 `notification.requested`를 낸다.
   ```sh
   ./scripts/app.sh notification-routing logs      # "ai summary routed eventKey=<storyId>:1 outcome=ROUTED targets=... published=..." 확인
   docker exec -i kachi-mongo mongosh --quiet kachi_notification_routing --eval \
     "db.routing_jobs.find({storyId: '$STORY_ID'}, {eventKey:1, status:1, targetCount:1, publishedCount:1, _id:0})"
   ```
   - `targets`와 `published`가 같아야 한다. job의 `status`는 `COMPLETED`다.
   - 수신자 수는 1단계 `recipients/search`의 `keywords`에 story의 `keywords`를 넣었을 때 나오는 `recipients` 항목 수다.
6. **접수·발송**
   - notification-service가 접수하고 worker가 보낸다.
   ```sh
   docker exec -i kachi-mongo mongosh --quiet kachi_notification --eval \
     "db.notifications.find({storyId: '$STORY_ID', recipientId: '$ADMIN_ID'}, {requestId:1, channel:1, status:1, failureReason:1, _id:0})"
   ```
   - 관리자의 세 채널이 `SENT`여야 한다. `requestId`는 `sum:{storyId}:{version}:u:{recipientId}:c:{CHANNEL}`이다.
   - `SUPPRESSED`면 사유(`failureReason`)를 본다.
     바인딩이 없거나 24시간 안에 같은 requestId로 이미 보낸 것이다.
7. **실제 수신**
   - Slack 채널, Discord 채널, Telegram 대화에 요약 메시지가 왔는지 눈으로 확인한다.
   - 본문 첫 줄은 `[<displayName>] <요약 제목>`이다. 대괄호 안은 그 수신자가 구독한 story 키워드의 displayName을 `, `로 이은 것이다.
   - 세 채널 모두 와야 끝이다.

## 재실행

같은 기사로 다시 돌리면 아무 일도 일어나지 않는다.

- collector는 이미 저장한 기사를 `duplicateCount`로 세고 이벤트를 내지 않는다.
- ai-service는 미요약 기사가 있는 story만 새 버전으로 요약한다.
- 같은 `ai.summary.created`를 다시 받아도 routing job이 `COMPLETED`라 `outcome=SKIPPED`다.
- 같은 `requestId`는 접수에서 걸리고, 24시간 안이면 `notification:sent:{requestId}` 가드에도 걸린다([알림-멱등-가드.md](알림-멱등-가드.md)).

다시 돌리는 방법:

- **같은 story의 다음 버전으로**: 그 story에 새 기사가 3건 붙으면 ai-service가 다음 버전을 요약한다.
  - 2단계 수집을 다시 부르거나 collector scheduler(10분 주기)를 기다린다.
  - 다음 버전은 `requestId`의 version이 달라 새 알림이다. `DEVELOPMENT` 판정일 때만 알림이 간다.
- **처음부터**: 사이클을 내리고 MySQL·Redis·Mongo·Kafka·Qdrant의 컨테이너와 volume을 지운 뒤 다시 띄운다.
  - 사용자·구독·바인딩, 기사, story와 색인, 요약, routing job, 알림, 발송 가드, Kafka topic과 consumer offset이 함께 지워진다.
  - 다음 `start`가 Flyway 스키마와 local 시드(관리자·바인딩·구독), Mongo 인덱스, Qdrant 컬렉션, topic을 다시 만든다. `kachi_tei-data`(TEI 가중치)는 남는다.
  ```sh
  ./scripts/cycle.sh reset
  ./scripts/cycle.sh start
  ```

## 정지

```sh
./scripts/cycle.sh stop
```

서비스 7개와 인프라, TEI 컨테이너를 내린다. 데이터는 compose volume에 남는다.
완전히 비우려면 `docker compose -p kachi down -v`를 쓴다. 이 명령은 TEI 가중치 volume(`kachi_tei-data`)도 지우므로 다음 TEI 기동은 [user-intervention.md](user-intervention.md) 3번부터 다시 한다.
